## 〇、背景：读懂本报告需要的最少上下文

**这个项目在做什么？** GitHub Issue #16（agent-hub-alpha 仓库）组织七个小团队（W01-W07）协作开发一个"年报多智能体演示系统"：用户在对话界面下达年报编制任务，系统生成一张任务执行图，多个专业 AI 角色按图协作完成报告并经核验交付。各工作包分工：W01 出银行年报材料和验收标准、W02 做用户界面、W03 做图执行引擎、W04 用 Go+PostgreSQL 做控制账本、W05 做 Agent 通信总线、**W06（本文主角）做报告专业角色和核验器**、W07 做部署。截至本文撰写时，除 W06/W07 外其余均已交付或认领。

**W06 的定位是什么？** 在最终架构里，系统按"三权分立"组织：
- **推进权**（决定下一个执行哪个步骤）归 W03 的图调度器；
- **提交权**（什么算"正式结果"）归 W04 的 Go/PostgreSQL——整个系统只有这一处有权写正式状态；
- **干活权**（实际生产报告内容）归 W06——我们提供六个专业角色节点（资料装载、指标抽取、三类财务分析、成稿、数值核验、引用核验、批准）。

W06 的角色节点内部可以用大模型干活，但**没有提交权**：一切产出必须回流给 Go 判定。因此 W06 与其他组件的接口契约是系统能否闭环的关键。

**几个反复出现的术语**：
- **交付谓词**：Go 侧判定一份报告能否交付的公式——数值核验通过 ∧ 引用核验通过 ∧ 用户确认 ∧ **三条记录绑定同一个工件指纹（artifact_sha256）**。最后这个条件意味着：核验结论必须注明"我验的是哪份文件"，否则改正文后旧的"通过"结论依然有效，等于没验。
- **E03**：验收反例集（#20 Issue）里的一条攻击用例——"检查完成后偷改正文，旧检查结果仍可放行"。防线就是上面的指纹绑定。
- **三形态同源**：W06 的核验规则以三种形态存在（Java 服务进程 / 技能包里的 Python 脚本 / MCP 协议工具），方案承诺三者规则完全一致，任何一处改动必须同步其余两处。
- **N1-N7**：数值核验的七条规则——完整性、单位、数字溯源、派生复算、同比复算、方向一致、变动口径。N7 是最后一条：比率变动必须写"百分点"，写成"%"即拦（0.94 个百分点 ≠ 下降 0.94%）。
- **GatekeepRail**：挂在成稿环节后的门禁组件（"Rail"是 openJiuwen 框架的扩展点概念）——核验失败自动打回修订一次，再失败转人工，绝不静默放行。
- **D1/D2**：#16 定的集成检查点。D1=2026-11-19 20:00（契约冻结），D2=2026-11-24 20:00（完整链路联调）。本报告的问题按这两个期限排修复优先级。

**本报告的"三形态"实证指什么**：①本地 Java 工程（`w06-annual-report-agent/`，构建产物将部署为独立角色容器）②线上演示服务（`192.144.137.185:18083`，工作台 + 核验服务一体）③技能包脚本（`skills/annual-report/scripts/*.py`，角色节点内自主执行用）。

## 一、致命级（违背方案核心契约，验收必挂）

### P1 · CheckResult 无 artifact_sha256 —— 交付谓词拼不上

**通俗说**：核验器给出"通过/不通过"结论时，没有同时声明"我验的是哪一份文件"。就像质检员在合格证上不填产品编号——文件被换掉后，旧合格证依然能蒙混过关。

- **方案要求**（§2.3/§3.1）：`CheckResult += artifact_sha256`，"核验结论绑定工件指纹，谓词里没有裸的通过"。
- **实证**：`contract/CheckResult.java` 仅 4 字段（checker_id/version/status/violations）；GatekeepRail 全文 **0 处** digest/sha256；线上 handleCheck 亦无。
- **影响**：E03 反例（检查后改正文，旧 PASSED 仍可引用）**当前可复现**——这是验收方明确要求演示的攻击防线；Go 的 `Deliverable(T)` 谓词在数学上无法装配 W06 侧输入——checks 表没东西可收。**这是方案与实现之间最大的一条断层**，D1 交付卡若演示 E03 防线即穿帮。
- **修法**（0.3 天）：record 加字段 → GatekeepRail 在 checker 返回后计算工件字节流 sha256 一并写入 verdict → 补 E03 反例测试（改正文 → 旧 verdict 判 INVALID）。

### P2 · 三形态规则集已分叉：N7 只存在于线上，本地与 skill 脚本均无

**通俗说**：同一套核验规则存在三份拷贝（Java 服务、Python 脚本、MCP 工具），本应完全一致。最近线上版本新增了"百分点"规则（N7），但另外两份拷贝没同步——用 Python 脚本核验的角色节点会放过"不良率下降 0.94 个百分点"被写成"下降 0.94%"这类错误，而这类错误恰好是 W01 材料验收反例集里明确要求拦截的。

- **方案要求**（§2.3）："三形态同源"——Java 进程/skill 脚本/MCP 面规则一致。
- **实证**：线上 checker（425 行，含 DELTA_PHRASE 正则+N7 DELTA_UNIT_MISMATCH）✅；**本地工程 checker 模块 N1-N6 无 N7**（grep N7=0，规则清单 N1-N6+BASE_/CALC_）；**skill 脚本 verify_metrics.py 百分点=0 处**。
- **影响**：①"三形态同源"承诺名存实亡——Trae 在线上加的 N7 没回流到我们的工程与 skill；②用 skill 脚本核验的 agent 节点会**放过 W01 反例集里的百分点错误**（不良率 0.94 个百分点写成"下降 0.94%"）；③本地跑测试与线上行为不一致，回归结果不可信。
- **修法**（0.4 天）：N7 逻辑从线上版回灌本地 checker + verify_metrics.py 补 DELTA_UNIT_MISMATCH 规则 + evals 加用例。**建议同时建立"规则变更三形态同步"纪律**（改任一处必须三处同步+evals 跟进）。

### P3 · 部署形态与方案 v3 节点化完全不符

**通俗说**：方案要求六个角色各自跑在独立容器里、注册到通信总线、由图调度器统一调用；但服务器上实际只部署了一个"all-in-one"演示容器，角色没有独立进程存在——W05 通信总线的负责人正在等 W06 交出可注册的角色，交不出来整个联调就停摆。

- **方案要求**（§2.7）：六节点独立进程、A2A 挂 RDC、被 BlueprintScheduler 调度。
- **实证**：线上 `w06-checker` 单容器承载全部（注册表/装配/MCP/演示 pipeline 都在一个 Java 进程）；`w06-a2a-wrapper` 是固定演示编排（固定任务上下文跑核验），不是被调度的专家节点；compose 里的六服务定义**从未在服务器上部署**（docker ps 只有 checker/a2a-wrapper）。
- **影响**：当前部署是"治理演示面"而非 v3 定义的"执行面"——xierongqiag2015 的 W05 D2 联调（等 W06 角色到 11-21）到来时**没有东西可挂**。
- **修法**（M3 计划内，但需提前验证）：先在本地 compose 把六节点起起来过一遍 agent-card 健康检查（compose 已写好，只欠 `docker compose up` 实测），把"从未跑过"的风险消掉。

## 二、契约级（接口字段缺失，联调时暴露）

### P4 · 无执行身份 o/a/b —— Contract-C 消费未开始
- **方案要求**（§3.2）：节点执行携带 `o=(T,g,node_path,iteration_path)`；同 o 重交复用语义。
- **实证**：contract 包无任何身份字段；GatekeepRail 的 revisionRounds 是"每会话一个 map"，与身份无关。
- **影响**：与 yougq 联调时 W06 节点提交的 observation 无身份 → Go 无法去重/复用/判代次 → S04/S05/S09 全挂。
- **修法**（0.5 天，M1 尾或 M2 头）：直接 import 他的 Contract-C 共享类型（08e2e40），字段进 MetricValue 提交与 CheckResult。

### P5 · 批准链不独立：approver 在主编 team 里
- **方案要求**（§2.6 R5）：批准官独立于主编，不被分派控制（E02 精神）。
- **实证**：seedAgents 里 approver 与其他 8 个一起进 editor-in-chief 的 team[]；handleTeamRegister 可对它 register/unregister。
- **影响**：演示 E02（伪造批准）防线时，"批准可被主编移出团队"这一事实本身就是反例素材；交付卡评审会被问。
- **修法**（0.1 天）：approver 从 team 种子移除 + handleTeamRegister 对 approver 拒绝注册。

### P6 · 骨架 metric_keys 缺失 → 输入注入无配置依据
- **方案要求**（§2.6 R6）：每 analysis 节声明消费指标子集，作为"互斥隔离"的配置依据与一致性校验。
- **实证**：线上 report-structure.json 各节只有 role/agent/label，无 requires/metric_keys；互斥隔离目前靠 skill 文档约定（agent-division.md 的工位表），**机器不可校验**。
- **影响**：三分析并行隔离是 N4 拦截的前提——没有配置依据的隔离，citation 核验的"越界引用"判定只依赖文本启发，可被"分析文本恰好提及他组指标词"误伤。
- **修法**（0.3 天）：sections 加 metric_keys → material/metrics 节点按声明注入 → citation-checker 越界判定改为查配置。

## 三、一致性级（治理面与方案模型不符）

### P7 · 注册表与方案 v3 的节点集合不一致（writer/capital 错位）
- **方案要求**（§1.2）：六节点 = material/metrics/finance∥risk∥capital/writer/checker/approver。
- **实证**：线上注册表 10 agent 里**无 writer、无 metrics-agent**，但有 disclosure-officer（三合一）和 chart-agent（无节可干）；Java 工程里 MetricAgent/WriterAgent 存在却未上注册表。
- **影响**：能力卡目录（给主 Agent 选图用）与真实可调用的节点集合对不上——主 Agent 若按注册表生成图会引用不存在的 writer 节点，Go 校验直接拒。
- **修法**（R1/R2 计划内 0.8 天）：注册表从骨架派生时同步落 writer/metrics 两节点。

### P8 · 主 Agent 知识包 orchestrator-skill 仍是"计划"，无一实体
- **方案要求**（§2.5）：SKILL.md/domain-brief/constraints/alk05 能力卡/evals 三例。
- **实证**：skills/ 下只有 annual-report 一个包；alk05-*.json 不存在；能力卡无 applies_to/constraints 字段。
- **影响**：ALK-05 三条验收用例（选择差异/高分排除/全 unknown 拒绝）**无任何实现可测**；主 Agent 当前生成不了有依据差异的图——"预录图伪装规划"的风险在我们侧成立。
- **修法**（0.8 天）：按方案 §2.5 目录树实体化（能力卡可从现有注册表+banking-domain 机械生成初版）。

### P9 · MCP 版本字段缺失（AR-04 侧）
- **方案要求**（§2.4）：能力卡/MCP 工具挂 version。
- **实证**：MCP_REGISTRY 的 putMcp 无 version 字段；AgentCard/注册表 seedAgents 有 version 但 MCP 无。
- **影响**：图采纳时绑不了工具版本 → 工具变更后无漂移检测。
- **修法**（0.1 天）：putMcp 加 version，tools/call 响应带 server 版本。

## 四、方案自身需修正的两点（审视反向发现）

1. **方案 §1.2 拓扑与线上骨架 14 节不对应**：方案画的是"六节点流水线"，但真实报告生成是骨架驱动的 14 节（S-1~S-14）。两者不矛盾（节点=工位、节=报告章节），但方案未写映射关系——补一句"工位×章节映射由 report-structure.json 承载"即可，否则评审会问"图到底长什么样"。
2. **运行面板的"9 节点轨迹"与 v3 拓扑不一致**：面板 n1-n9 是编排演示序列（含主编规划节点），而 v3 定义主 Agent 不在执行图内（它生成图不执行图）。演示时两套口径会打架——面板应改口径为"候选图生成过程演示"或按 v3 拓扑重排。
